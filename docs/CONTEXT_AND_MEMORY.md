# 上下文与记忆设计

## 四类数据各司其职

| 数据 | 所属范围 | 用途 | 是否修改原始聊天 |
| --- | --- | --- | --- |
| 原始消息 | 会话 | 完整历史、导出、项目历史检索与核对来源 | 不适用 |
| 会话检查点 | 单个会话 | 压缩较早消息后继续对话 | 否 |
| 用户记忆 | 全局或项目 | 跨会话保留稳定事实、偏好 | 否 |
| 模板记录 | 项目＋模板 | 训练记录、计划等结构化业务事实 | 否 |

检查点不能升格为用户记忆，也不能替代模板记录。模型从项目历史或记忆获取的信息是线索；需要精确训练数据时，应使用授权的模板能力读取记录。

## 当前实现

- 聊天请求先检查已有检查点是否匹配当前可见分支的消息前缀。修改历史消息、切换分支或删除消息后，指纹不匹配的检查点失效并重建。
- 上下文超过“最多上下文消息数”，或已登记模型上下文窗口的约 60%（保守估算）时，摘要较早消息，保留近期消息原文。摘要使用当前 Provider 的模型，不调用工具；失败时保持原始聊天及旧检查点不变，按原有最近消息策略继续。
- 原始消息始终保存在 Room；新增的 `conversation_checkpoints` 表仅保存当前会话的续接摘要。数据库从 18 升级到 19，不清除旧数据。
- 每轮聊天注入当前可见的至多 8 条全局／本项目记忆，并继续提供 `memory_search` 工具。用户可在“设置 → 记忆管理”新增、修改、删除、按范围查看；项目详情菜单可直达本项目记忆。AI 写入仍受“允许 AI 写入记忆”开关控制。
- 完全相同的同范围记忆保存请求幂等，不会重复插入；不同表述的重复或冲突记忆仍需用户检查并修订。

## 后续边界

本阶段没有启用后台自动提炼长期记忆，避免把模型推测、敏感信息或已经过时的计划静默保存为用户事实。若未来增加自动提炼，应先实现候选预览、来源标注、冲突检测与用户确认；不把训练记录复制成自然语言记忆。
