# 健身服务：协议 2 契约与验收

初版日期：2026-09-17；流程核对：2026-09-20。本设计重新实现已确认的健身原型，不兼容旧模板或恢复旧数据。

## 数据与操作

实例按项目、模板隔离，模板 ID 为 `mutcube.fitness`，版本为 `2.1.0`。从 2.0.0 升级需重新确认新增集合权限；原集合契约与已有训练数据保留。

| 集合 | 策略 | 内容与操作 |
| --- | --- | --- |
| profiles | IMMUTABLE_HISTORY | 用户资料快照；GUI 保存，GUI/CHAT 查询 |
| drafts | MUTABLE | 当前训练草稿；GUI 新增/修订，只有 GUI 可读取 |
| training | IMMUTABLE_HISTORY | 每自然日一份实际训练，日期为稳定提交键；GUI 提交，GUI/CHAT 查询 |
| requests | IMMUTABLE_HISTORY | AI 请求及宿主注入的资料、当前计划、最近训练 |
| plans | VERSIONED | AI 计划候选；GUI/CHAT 查询和生成，仅受信任 GUI 可视化预览后点击启用 |
| profile_drafts | MUTABLE | 表单、最近交流和未发送文字，仅 GUI 暂存/更新/读取，不是正式资料 |
| profile_requests | IMMUTABLE_HISTORY | 资料整理请求、当前表单、近期交流、可选宿主正式资料 |
| profile_candidates | IMMUTABLE_HISTORY | AI 的回复、待核对字符串资料字段及 ready 标识，不自动保存 profiles |

计划生成公开输入为 request、baseRevision、targetDate；profile 为必需 LATEST binding，current_plan 为可选 CURRENT binding，last_training 为可选 LATEST binding。聊天不能伪造这三个字段，也不能直接写资料、草稿或训练事实。最近训练不等于完整训练历史；必要时聊天应分页查询 training.list。

`plan.current` 是最近确认版本及其修订指针，供生成来源、并发检查和追溯使用，**不等同于仍可执行的日计划**。训练页的“待执行计划”由该指针与已提交训练记录共同推导：若该版本的键已被实际训练引用，就显示“暂无”；已完成内容转到“记录”，“我的训练”只把它标为上一份已完成计划。候选在用户启用前既不替换版本指针，也不属于待执行计划。

资料必填身高、体重，默认训练目标、频率、分化；经验、器械、限制以及熟悉动作工作重量选填。不要求极限测试，哑铃按单只重量。工作重量建议覆盖推、拉、蹲、髋铰链四种模式，允许用户留空或说明替代动作。

实际记录保存日期、原计划键、计划快照、各组重量/次数/RIR、备注。允许保留原计划草稿，提交不会偷偷改用当前新计划；因此提交不绑定 CURRENT。结构化业务数据通过声明授权获取。宿主还提供只读项目会话检索（见 PROJECT_CONTEXT.md），聊天证据不会自动写入训练日志、资料或基线。

## 交互流程

1. 首次进入无资料可选“和 AI 交流（推荐）”或“直接填写”；已有资料直接进入训练页。两种入口随时切换，共享字段，交流/表单/未发送文字保存为草稿，退出失败则留在页面。AI 整理 action 为 profile.assist，仅 GUI 可调用；宿主注入正式资料并提供项目历史只读检索，模板指令要求不猜测身高体重、只追问必需项和冲突、指出证据待核对。用户点击核对后进入可编辑表单，手动保存才追加正式 profiles，资料保存后不自动启用新计划。资料整理失败保留用户描述，可再次点击重试或转表单。
2. 无已启用计划时可请求 AI 生成首份计划；AI 返回的是持久化候选，训练页预览动作、重量、组数、次数区间与 RIR，用户点击“启用计划”后才切换当前版本。当前版本与候选不是同一种状态；聊天没有启用权限。
3. 最近确认但尚未用于已提交训练的计划，显示为“待执行计划”，并在未有当日训练事实时形成草稿：重量和组数按目标预填，次数与 RIR 保持未填。每组以紧凑数值格呈现，点击后打开底部编辑层，可用目标下限、加减或数字输入；取消不记录，确认后才写入草稿。重量可直接输入，组数可增减，整项动作可从当天草稿移除并在提交前恢复；这些操作不修改已确认版本或历史记录。
4. 输入停止后防抖保存草稿；离开或切换聊天前等待保存。失败留在页面；强杀前最后一次修改仍可能未保存。已有实际输入时若启用新候选，当天填写页立即切至新计划；旧草稿保留，可显式恢复。恢复旧草稿不会反向修改当前计划，也不会自动把旧成绩迁移到新动作。
5. 提交前检查日期、非空动作及全部实际组的重量、次数、RIR；每自然日最多一份实际记录。先以 training-YYYY-MM-DD 保存不可覆盖的事实，再标记草稿已提交，然后请求 AI 生成下一次计划。生成失败不回滚事实，重试不重新提交事实。
6. 已提交记录使用的计划即使仍是 CURRENT，也不被视为可自动重复使用的每日安排：训练页的“待执行计划”显示“暂无”，次日不按这份旧计划生成待填草稿。旧版错误生成但尚未填写的同计划空草稿也不再展示，已有实际输入的草稿不会静默丢失。若下一计划尚未启用，页面显示“等待下一次训练计划”、最新候选预览/启用入口及生成或重试入口。确认新候选当天若已有训练记录，只保留新版本，不建立会被误判为已提交的同日草稿；下一训练日再建立草稿。此规则不删除旧计划、候选或历史。
7. 训练页只显示最新候选，不删除底层历史版本。预览并通过业务范围检查后，受信任内置 GUI 中点击“启用计划”直接生效，不重复弹出 JSON 原生确认；源版本不匹配时须重新生成。
8. 日历分页加载完整实际记录，标记已提交日期；点击日期显示当天计划快照、动作、重量、次数、RIR及备注。草稿不标记为已训练。
9. 模板可进入正常项目聊天；同项目聊天按授权查询资料、训练事实、当前计划并生成调整候选，不能直接改写事实或启用计划。模板 GENERATE 还可受控检索项目其他会话作为证据；该证据不会自动变成正式资料或训练记录。返回模板后刷新候选，确认前当前计划不变。

一天一份记录为当前产品边界，同日多场次不支持；不覆盖已提交记录。不在宿主添加任何健身数据字段、业务分支或特殊数据库操作。

目前计划的 `targetDate` 是目标提示，不是提交日期的硬限制：未提交当日训练时，用户仍可提前填写未来目标日期的计划。是否禁止提前执行需另行确定产品规则；不要在模板或宿主中无提示地改写用户选择的日期。

补录历史日期时，生成的下一计划默认日期为“实际训练日期的次日”与“今天”中较晚者；今天已提交记录后重开页面，默认目标日期为明天。模板在跨天重新显示时更新日期，不继续使用 WebView 初次加载时的旧日期。旧日期尚未提交的有实际输入草稿仍可从新计划切换入口恢复。

## 验收边界

页面脚本测试覆盖真实页面逻辑，Room 仪器测试使用隔离数据库；真实 Provider 测试需显式 opt-in，并只读取已有凭据。它们分别验证不同边界，不能互相替代。实际用户库不提交虚构训练。设备 GUI 检查与真实模型结果记录在 PROGRESS.md。
