## 首版流程

1. 未填写基本信息时进入表单；身高、体重必填，训练目标、频率、分化有默认选项。训练经验、器械、动作限制和熟悉动作工作重量选填。哑铃重量按单只记录，不要求测试极限重量。
2. 保存基本信息后进入训练页，没有计划时展示生成入口；先预览并确认首份计划。
3. 每个动作显示建议重量、组数、次数范围和 RIR。实际重量预填，按组填写实际次数与 RIR，允许增减组数；输入持久化为草稿。
4. 提交先保存实际记录，随后生成下一次计划；失败只重试计划生成，不重复提交记录。新计划确认前不替换当前版本。
5. 日历标记已提交记录日期，点击查看实际训练，不把草稿视为已训练。首版原型每自然日一份提交记录，多次训练场次后续需单独确定。
6. “我的”可编辑基本信息、查看模拟运行状态；编辑偏好不自动替换已确认计划。
7. 模板菜单及“我的”提供计划讨论入口，模拟正常项目聊天。调整需预览、确认，再保存新计划版本；历史记录不由 AI 覆盖。

## 模板与原生边界

- 模板负责表单、动作卡片、日历、训练规则及业务数据契约。
- 原生负责项目身份、凭据引用、能力授权、JSON 校验、持久化事务、运行记录与备份。
- 第一阶段通过授权的候选生成与当前版本选择能力调整计划；普通聊天不能直接覆盖数据库中的训练事实。
- 正式实现应验证提案的源计划版本，防止过期提案覆盖新计划；计划调整时已有草稿不能静默清空，应让用户选择保留原计划草稿或重新录入。
- 项目选择及授权继续使用宿主入口；本原型固定展示“我的训练”作为项目示例，不模拟真实授权。

## 原型限制与评审重点

固定动作及重量只是演示内容，不是模型生成的训练处方；不同目标和分化尚不驱动示例变化。计划讨论为固定提案，非真实 AI 回复。数据保存在浏览器独立命名空间，不接入真机数据，也不填写用户 Key。

检查表单信息量、动作卡片的录入便利性、提交与计划确认的分离、生成失败后的提示，以及日历回顾和讨论返回模板是否顺畅。再根据用户反馈迭代原型，确认后实施业务代码。

本轮内联脚本语法及 git diff 检查通过；自动浏览器访问本地文件被安全策略拒绝，不绕过限制，点击和视觉验收待手动打开完成。

## 实际接入进度

- 业务 JSON 契约由 FitnessTemplate 定义，资料、草稿、已提交训练和 AI 计划分别存储；复用原生模板能力与项目 Provider，不创建显性聊天。
- 资料和草稿当前采用不可覆盖的追加快照，读取最新一份；草稿输入停止约 800 毫秒后保存，提交前等待保存完成。正常宿主返回及切换聊天先等待草稿保存，失败保留页面；相同草稿内容不重复追加。系统强杀/崩溃、应用切后台的即时刷新和快照整理仍待补齐。
- 实际记录使用日期作为稳定请求标识，重复同内容提交幂等，不允许不同内容覆盖同日记录。先保存事实，再生成下一次计划；计划生成失败不回滚事实。
- 首份/下一份计划通过真实 AI 生成，经过模板业务目标校验，预览后调用原生版本确认；读取当前指针恢复已确认版本。已有次数、RIR、备注、重量或组数变化的草稿时，可选择保留原计划继续录入，或启用新计划并重新录入；旧草稿快照不删除、不视为训练事实。
- 日历通过时间与键双游标分页读取完整已提交历史，不再限制为一百条。模板内可直接填写计划调整要求；已授权项目聊天提供当前版本读取和候选生成工具，必须回到模板确认。项目聊天及项目详情提供训练模板入口，升级须重新确认能力授权。
- 健身定义升级为 1.1.0，新的计划请求使用 plan_requests_v2，保留旧集合契约与已确认计划。候选记录关联 baseRevision，生成提交和启用均校验源版本；过期或旧协议候选提示重新生成，不自动替换计划。
- 2026-09-17：数据库 29 项真机仪器测试通过（包含 103 条历史分页）；独立健身提案/权限竞态及备份测试 2 项通过；实际页面脚本的隔离桥接测试通过。真实 Provider 与逐页面验收另行记录，不把替身测试当作真实 MiMo 验收。
